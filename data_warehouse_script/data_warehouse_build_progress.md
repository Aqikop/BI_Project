## 2. Platform decision

The team first planned PostgreSQL with Python scripts, then switched to **SQL Server with Visual Studio (SSIS)**.

- Reason: after studying and experimenting, Visual Studio was more convenient for working with SQL Server and easier to follow against the lecturer's examples. The warehouse platform is a free choice.
- Environment: SQL Server Developer edition (17.0) on the same instance as the source database `CompanyX`; SSMS for queries; Visual Studio with the SSIS extension for packages (project `CompanyX_ETL`).
- The warehouse is a **separate database** (`CompanyX_DW`), so the source stays untouched and the OLTP/warehouse separation is clear.
- Mining stays in Python (Apriori/FP-Growth via mlxtend), reading from the warehouse and writing back to `AssociationRulesFact`.

Supporting objects:
- Schemas: `staging`, `dw`, `etl`.
- Staging tables: `staging.ProductVersion`, `staging.Customer`, `staging.OrderLine`.
- ETL control: `etl.Watermark`, `etl.RunLog`, `etl.ReplayConfig`, view `etl.vReplayWindow`, procedure `etl.usp_ReplayReset`.

### Key design decisions in force

- **Naming:** every table ends with its type (`DateDim`, `ProductDim`, `CustomerDim`, `OrderLineFact`, `AssociationRulesFact`).
- **Mining grain:** Product Model (`ProductModelID`), not SKU. The warehouse stores model names on `ProductDim`.
- **Rules table columns:** `AntecedentModelID`, `ConsequentModelID`, their names, `Support`, `Confidence`, `Lift`, `AntecedentSupport`, `ConsequentSupport`, `CoOccurrenceCount`, `RuleClassification` (`Bundle`, `Hidden gem`, `Chance`, `Substitute`, `Weak`), `Channel` (`Individual` or `Reseller`), `GeneratedDate`.
- **Mining channels:** individual run is the main analysis, reseller run is a comparison; no pooled run. Single-model orders stay in the support denominator.
- **Load scope (provisional option A):** only shipped orders (`Status = 5`) are loaded, so there is no `Status` column in the fact table. The team keeps this open for further discussion.
- **Customer load rule:** customers with `PersonID IS NOT NULL` (19,119). `StoreID IS NOT NULL` marks a Reseller.
- **Anomalous lines** (null, zero or negative quantity or price) are 75 lines in six orders, 43677 to 43682. They stay in the fact table so revenue reconciles and are also logged in `etl.OrderLineAnomaly`; mining must use only lines with `OrderQty > 0 AND UnitPrice > 0`.
- **Retired products:** 71 lines for retired products ordered after their price history ended use the product's latest version instead of being dropped.

## 5a. Transformations (the T in ETL)

Most transformations are written as SQL in the source queries and load tasks (an ELT style: extract, load to staging, transform in the database). To make the T visible, part of it was moved into SSIS data flow components. Results were identical after the change (full replay: 353 / 19,119 / 120,147 / revenue 108,734,796.040861).

| Package | SSIS component | Transformation |
|---|---|---|
| `LoadCustomerDim` | Derived Column | `CustomerType` = Individual when `StoreID` is null, otherwise Reseller; `StoreName` = "N/A" when missing |
| `LoadOrderLineFact` | Derived Column | `DateKey` (YYYYMMDD from `OrderDate`); `DiscountAmount` = `OrderQty` x `UnitPrice` x `UnitPriceDiscount`, NULL when quantity or price is NULL |
| `LoadOrderLineFact` | Lookup | `CustomerKey` from `dw.CustomerDim` (match on `CustomerID`, fail if no match) |
| `LoadOrderLineFact` | Multicast + Conditional Split | Lines with null, zero or negative quantity or price are logged to `etl.OrderLineAnomaly` while still loading into staging (75 lines, equal to the anomalous lines in the fact table) |

Transformations that stay in T-SQL:

| Where | Transformation | Why it stays in SQL |
|---|---|---|
| `ProductDim` source query | Merge of price and cost histories, hierarchy joins, "as of" version dates and `IsCurrent` | Depends on the replay window view |
| `LoadOrderLineFact` load task | `ProductKey` found by order date within a version's date range, with a fallback to the latest version | A standard SSIS Lookup matches on equality and cannot express a date range with a fallback |
| Dimension load tasks | SCD2 close-and-insert, SCD1 overwrite, change detection with `EXCEPT` | Set-based SQL is simpler and easier to verify |
| `DateDim` | Generated from a calendar | No source table |

Checks run after the change: final counts unchanged; customer split 18,484 Individual (all "N/A") and 635 Reseller; anomaly log 75 = 75 anomalous fact lines; discount mismatches 0; orders by channel 27,382 / 3,768; individual multi-model orders 17,805.

## 7. Replay design (near-real-time simulation)

The dataset is a fixed historical snapshot, so a replay simulates live data arriving over time.

- **Clock:** the `dw.OrderLineFact` row in `etl.Watermark` holds the date up to which orders are loaded.
- **Window:** `etl.vReplayWindow` returns `FromDate` (exclusive) and `ToDate` (inclusive = `FromDate` + `WindowDays`, capped at the last date in `DateDim`). `WindowDays` lives in `etl.ReplayConfig`.
- **Windowed queries:** the `ProductDim` and `OrderLine` source queries join the window view, so `ProductDim` shows only the price versions that exist as of `ToDate` and the fact table receives only orders inside the window. No SSIS variables or parameters are needed.
- **Dimensions:** `CustomerDim` and `DateDim` load in full (no history in the source).
- **Advance:** the `AdvanceWatermark` task in `MasterLoad` runs only if all three loads succeeded; it moves the clock to `ToDate` and writes a row to `etl.RunLog`.
- **Reset:** `EXEC etl.usp_ReplayReset;` empties the fact table and both dimensions and rewinds the clock to 2011-05-30 (keeps `DateDim` and `AssociationRulesFact`).
- **Why it matters:** price changes happen on only three dates (2011-05-31, 2012-05-30, 2013-05-30), so the replay must cross 2012-05-30 and 2013-05-30 for SCD2 to create versions.

### Replay test results

| Test | Result |
|---|---|
| Catch-up to 2012-05-22 (window 358 days) | 62 product versions, all current; 10,485 fact lines; clock 2012-05-22 |
| First weekly run (clock 2012-05-29) | 62 versions, 62 current, 0 closed (no gap after the `>=` fix; before the fix it was 62 / 0 / 62, see section 8) |
| Second weekly run (clock 2012-06-05, crosses the 2012-05-30 price change) | 170 versions, 108 current, 62 closed (62 + 108 new versions) |
| Final full replay (clock capped at 2014-06-30) | 353 versions, 19,119 customers, 120,147 lines, revenue 108,734,796.040861; **identical to the one-shot load** |

The match with the one-shot load is the main evidence that the incremental logic is correct.

## 7a. Scheduling

- **Deployment:** project `CompanyX_ETL` deployed to the Integration Services Catalog (`SSISDB`), folder `CompanyX_DW_test`, with `LoadProductDim`, `LoadCustomerDim`, `LoadOrderLineFact` and `MasterLoad`. Protection level `DontSaveSensitive` (connections use Windows authentication).
- **Job:** SQL Server Agent job `CompanyX_DW_Replay_test`, one step (type SQL Server Integration Services Package, source SSIS Catalog, package `\SSISDB\CompanyX_DW_test\CompanyX_ETL\MasterLoad.dtsx`, run as the SQL Server Agent service account).
- **Schedule:** recurring daily, every 1 minute, no end date.
- **Verification:** a manual start of the job succeeded, and `etl.RunLog` gained a `MasterLoad` row (run 1016) with the clock moving to 2013-05-15 and 24,564 lines loaded.
- **Note:** that first job run advanced 358 days (2012-05-22 to 2013-05-15) because `WindowDays` was still at the catch-up value. Set `WindowDays` to the intended size (7 or 30) before letting the schedule run.
- **Replay completed by the job:** the schedule carried the clock from 2013-05-15 to 2014-06-30 in two further runs (the window was still 358 days, so the last runs were 2013-05-15 to 2014-05-08 and 2014-05-08 to 2014-06-30, the latter with 6,280 lines). `etl.vReplayWindow` then showed FromDate = ToDate = 2014-06-30, 0 days left, status DONE. Later runs (1019, 1020) loaded 0 rows.
- **Final state after the scheduled replay:** 353 product versions, 19,119 customers, 120,147 fact lines, revenue 108,734,796.040861, identical to the one-shot load.
- **When the replay ends:** once the clock reaches 2014-06-30, later runs load nothing but still write a `RunLog` row. Disable the job at that point.

## 7b. Mining stage (summary)

Full results, tables and caveats are in `association_rule_mining_results.md`; the code is `association_rule_mining.ipynb`.

- **Method:** FP-Growth pair rules at Product Model level, minimum support 1%, from shipped orders with `OrderQty > 0 AND UnitPrice > 0`. Individual run is the main analysis (from 2013-05-30, 22,008 orders); the reseller run (3,762 orders) is a comparison. Single-model orders stay in the support base.
- **Stored rules:** 126 individual and 2,836 reseller (2,962 rows in `dw.AssociationRulesFact`). The reporting view `rpt.AssociationRules` shows the plain labels (Bought together, Under-promoted pair, Popular by coincidence, Weak link, Alternatives) and plain column names; the table keeps the brief's labels.
- **Validation:** time split (train 2013-05-30 to 2013-12-31, test Jan to Jun 2014): 62 of 68 strong rules hold, median lift ratio 1.00, rank correlation 0.98; June 2014 check leaves the holding set unchanged; sensitivity grid supports the 1% threshold; 22 pairs are strong in both channels.
- **Use cases:** Water Bottle → Hydration Pack (+6,735 at 5% conversion, no discount), Cycling Cap → Short-Sleeve Classic Jersey (+967), Mountain Tire Tube → LL Mountain Tire (+680 on a conservative reach), extra Road-750 → Road Bottle Cage (+247), and the rejected Touring-1000 → Sport-100 (lift 1.59 falls to 1.44 in 2014). Conversion and discount are assumptions; a discount never beats no discount at equal conversion.
- **Checks on the reseller base:** all four categories first sold to resellers on 2011-05-31, and the use-case models were checked at model level (first sales reported as 2011-05-31 and 2011-05-30; the earliest order date in the warehouse is 2011-05-31, so confirm the latter).
- **Seasonality:** tested as a light check and moved to an appendix; seasonal timing of offers is a limitation.

## 8. Issues found and how they were resolved

| Issue | Resolution |
|---|---|
| SSIS task name `Truncate staging.ProductVersion` rejected (dots are not allowed in task names) | Task names must not contain `/ \ : [ ] . =`; use plain names |
| `GO` and a result-returning `SELECT` do not belong in an SSIS Execute SQL Task | Paste only the `UPDATE` and `INSERT` statements |
| Expected 1,126 `DateDim` rows, got 1,127 | 1,126 is the day difference; counting both end dates gives 1,127 (correct) |
| Expected 59 lines for orders 43677 to 43681, got 70 | Order 43681 has 21 anomalous lines (not 10), so the five orders hold 12 + 19 + 3 + 15 + 21 = 70 lines, all anomalous. A sixth order, 43682, has 5 more lines with quantity 0, giving 75 anomalous lines in total. Section 2.2 of the project report understated this (five orders, 43681 at 10 lines) and should be corrected. Staging equals the source, so nothing was lost |
| After moving the `CustomerType` rule into an SSIS Derived Column, the split came out reversed (Individual 635, Reseller 18,484) | The expression had its branches the wrong way round (`ISNULL(StoreID) ? "Reseller" : "Individual"`). Fixed to `ISNULL(StoreID) ? "Individual" : "Reseller"`; rerunning `LoadCustomerDim` overwrote the labels (SCD1), and the split now reads 18,484 Individual / 635 Reseller. The check on the customer split caught it |
| Derived Column rejected `L"N/A"` | SSIS string literals are already Unicode; the `L` prefix is invalid. Use `"N/A"` with an explicit cast |
| SQL check comparing two `IS NULL` conditions with `<>` failed | T-SQL cannot compare boolean conditions; rewritten with explicit `AND`/`OR` |
| Shipped revenue (108.73M) below the 109.8M quoted in Section 2.2 | Cancelled orders (315) are excluded under the shipped-only load rule |
| After the first weekly replay run, no product had a current version (62 closed, 0 current) | As-of artifact: every first-period version ends on 2012-05-29, the clock date, while its successor starts 2012-05-30. **Fixed:** the `ProductDim` source query now uses `lp.EndDate >= w.ToDate` instead of `>` (two places), so a version closes on the day its successor appears. Replay tests T1 to T7 were rerun after the fix and the first weekly run now shows 62 / 62 / 0 |
| Package file named `MaterLoad.dtsx` | Cosmetic typo; renamed to `MasterLoad.dtsx` |
| Test/train lift ratio of 0.68 read as regression to the mean | Denominator artefact: individual customers could not buy accessories or clothing before 2013-05-30, yet 5,374 earlier orders were in the support base (16,363 training orders vs 10,989 after launch; 1 ÷ 1.49 ≈ 0.67). Fixed by starting the individual analysis on 2013-05-30; the ratio is now 1.00 |
| Mining notebook reconciled to a hard-coded 17,805 | The figure belonged to the old base; replaced by an independent count inside SQL |
| Net profit of +514 for the tyre bundle | Reach was overstated (customers already holding another tyre were counted); refined reach 869 gives −613 at a 10% discount, so the bundle was replaced as primary use case |
| Seasonal indices dominated by the accessory launch | Quarterly zeros were the 2013-05-30 launch, not seasons; section kept as an appendix and seasonality listed as a limitation |
